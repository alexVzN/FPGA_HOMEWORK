ЧАСТИНА 1. КОНТРОЛЕР ЗАМКА (ЗАНЯТТЯ 6)

1) Написати модуль lock_controller з РІВНО такими портами
   (назви важливі — тестова перевірка підключається саме
   до цих імен):

     input  clk           — тактовий сигнал
     input  rst           — асинхронний reset, активний
                             високим рівнем
     input  [3:0] digit_in
     output unlocked_led  — вихід, 1 = розблоковано

   Код — три цифри, оберіть довільні значення самі
   (наприклад, 5, 3, 7 — за зразком, як зручно).

   ЧОТИРИ стани: LOCKED, WAIT_D2, WAIT_D3, UNLOCKED.
   Переходи: LOCKED -> WAIT_D2 (якщо digit_in == 1-ша цифра
   коду), WAIT_D2 -> WAIT_D3 (якщо digit_in == 2-га цифра),
   WAIT_D3 -> UNLOCKED (якщо digit_in == 3-тя цифра). З БУДЬ-
   ЯКОГО стану — неправильна цифра повертає в LOCKED. У стані
   UNLOCKED лишається в UNLOCKED (не скидається саме по собі).
   unlocked_led = 1 ТІЛЬКИ в стані UNLOCKED, інакше 0.

   Three-process pattern — вимога до СТРУКТУРИ коду: РІВНО три
   окремі always-блоки, кожен відповідає за одну річ і більше
   ні за що:
   - один always-блок — ЛИШЕ реєстр стану (копіює next_state
     у state на фронті такту, нічого не вирішує);
   - один always-блок — ЛИШЕ логіка переходів (рахує
     next_state за поточним state і digit_in, нічого
     не виводить назовні);
   - один always-блок — ЛИШЕ логіка виходу (рахує unlocked_led
     із поточного state, не займається переходами).

   Не поєднуйте ці три відповідальності в одному always-блоці —
   саме роздільність на три блоки й перевіряється.

2) Написати testbench: правильна послідовність із 3 цифр
   (перевірка кожного переходу окремо: LOCKED->WAIT_D2,
   WAIT_D2->WAIT_D3, WAIT_D3->UNLOCKED) І сценарій помилки
   (неправильна цифра на будь-якому кроці -> повернення
   в LOCKED).

3) Додати debounce-фільтр для digit_in, який надходить
   із фізичних кнопок.

ЧАСТИНА 2. АНАЛІЗ TIMING SUMMARY REPORT (ЗАНЯТТЯ 7)

Мета тут — отримати число WNS 

1) Відкрити будь-який ваш попередній проєкт із довшим шляхом.
   РЕКОМЕНДОВАНО: alu.v (окремий лекційний приклад, порти:
   clk, rst, a[3:0], b[3:0], op[1:0], oe, result[3:0]) — його
   входи РЕЄСТРОВІ (a_reg/b_reg/op_reg), тому мінімальний .xdc
   з пункту 2 працює одразу, без жодних додаткових проблем.

2) Написати для нього .xdc-файл,  РІВНО один рядок, період задати 10-20 ns,
   можна поексперементувати.

     create_clock -period <ваше_число> -name sys_clk [get_ports clk]

3) У Vivado запустити: Flow Navigator -> Run Implementation (дочекатись
   завершення, НЕ зупинятись на Synthesis).

4) Відкрити вкладку Timing Summary (з'являється автоматично
   після Implementation) або Reports -> Timing -> Report
   Timing Summary.

5) Зробити скріншот вкладки Timing Summary з видимим рядком
   WNS (той самий скріншот, що додаєте в репозиторій разом
   із кодом).

ЧАСТИНА 3. НЕКОНВЕЄРИЗОВАНИЙ І КОНВЕЄРИЗОВАНИЙ ВАРІАНТ (ЗАНЯТТЯ 7)

1) Взяти файли expr_plain.v і expr_pipelined.v (додаються
   окремо, уже написані й перевірені запуском — можна
   використати як є) чи написати власний довгий вираз у двох
   варіантах: без конвеєра і з одним проміжним регістром.
   За власний варіант максимум 25 балів, за готовий 20 балів :)

   ВАЖЛИВИЙ ДИЗАЙН-ВИБІР, який варто повторити у власному
   варіанті: ВХОДИ РЕЄСТРОВІ (a_reg, b_reg, c_reg, d_reg),
   той самий принцип, що в alu.v  Без реєстрових входів шлях "порт -> перший
   регістр" лишається БЕЗ жодного тактового визначення
   (Vivado не знає, коли саме дані реально приходять на пін),
   і весь Timing Summary показує WNS=inf замість реального
   числа. Реєстрові входи прибирають цю проблему повністю:
   усі шляхи в дизайні стають регістр->регіст.

2) Створити для expr_plain.v .xdc — цей .xdc потрібен ЛИШЕ для аналізу WNS,
   не для реальної роботи на платі. Файл містить так само РІВНО
   один рядок:

     create_clock -period <ваше_число> -name sys_clk [get_ports clk]

   Задати досить високу частоту (ДОСИТЬ ВИСОКУ, щоб WNS
   вийшов негативним, краще в межах -0,5 -1 нс) підбирайте експериментально,
   почніть,наприклад, з періоду 4 нс.

   Якщо на вкладці Methodology з'явиться категорія
   "Unconstrained Paths" — це ознака, що десь у вашому
   власному варіанті лишився незареєстрований вхід; перевірте
   пункт 1 ще раз.

3) Run Implementation, WNS має бути негативним.
   Зробити скріншот вкладки Timing Summary
   з видимим WNS (файл screenshot_before.png у репозиторії).

4) Створити ОКРЕМИЙ проєкт (чи замінити джерело в тому
   самому) для expr_pipelined.v, з ТІЄЮ САМОЮ тактовою
   частотою (той самий -period у create_clock).

5) Run Implementation, зробити такий самий скріншот, якщо WNS 
   буде додатній, якщо ні, повторити з п.2
   (screenshot_after.png).

6) Для одного і того ж періоду WNS має бути негативним для 
   expr_plain і позитивним для expr_pipelined.
